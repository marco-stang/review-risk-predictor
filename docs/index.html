Portfolio-Projekt · Explainable ML

Warum wird diese Bestellung wahrscheinlich schlecht bewertet? Und woher weiß das Modell das?

Ein Full-Stack-Portal (React + FastAPI), das für Olist-Marktplatz-Bestellungen das Risiko einer schlechten Kundenbewertung vorhersagt — mit SHAP-basierter Treiber-Analyse und einer LLM-generierten Klartext-Erklärung statt einer bloßen Blackbox-Zahl.

Live-Demo öffnen GitHub-Repo ansehen

Was das Portal macht

Vier Schritte von der Rohbestellung bis zur verständlichen Erklärung.

1

Vorhersagen

Ein GradientBoostingClassifier schätzt pro Bestellung das Risiko einer schlechten Review (≤ 2 Sterne) aus Lieferzeit, Preis, Kategorie, Artikelanzahl und Verkäufer-Historie.

2

Erklären

SHAP (TreeExplainer) bestimmt die drei wichtigsten Einflussfaktoren pro Vorhersage — konkrete Zahlen, nicht nur eine Ampel.

3

Formulieren

Ein LLM übersetzt die SHAP-Treiber in 1-2 verständliche Sätze auf Deutsch — beeinflusst aber nie die Vorhersage selbst.

4

Anzeigen

React-Frontend: Bestell-Liste mit Risiko-Ampel, Detail-Ansicht mit Treiber-Chart, aggregierte Feature-Wichtigkeits-Übersicht.

Modell-Metriken

Zeitlicher Testset-Split (~20 % der Bestellungen, keine zufällige Durchmischung). Das Modell ist konservativ: sagt es „hoch“, stimmt es meistens (hohe Precision), übersieht aber auch einen Teil der schlechten Reviews (niedriger Recall). Für eine Portfolio-Demo der Explainability-Methodik ausreichend — kein Anspruch auf produktionsreife Vorhersagegüte.

Architektur

Offline-Pipeline schreibt einen SQLite-Snapshot; FastAPI liest nur daraus — kein Live-Postgres, kein Live-LLM-Call zur Laufzeit der App.

Olist-CSVsRohdaten
→
build_features.pyFeature-Engineering
→
train_model.pyGradientBoosting
→
explain.pySHAP
→
narrate.pyLLM-Erklärung (einmalig)
→
SQLite-SnapshotFastAPI + React

Kein Live-Postgres

Die Olist-Daten werden einmalig offline zu einem SQLite-Snapshot verarbeitet und mit ins Repo übernommen — kein zweiter, dauerhaft laufender DB-Service nur für dieses Projekt.

Stichprobe statt Vollständigkeit

~500 von ~100.000 Bestellungen (über Risiko-Terzile stratifiziert) — ein LLM-Call pro Bestellung für den ganzen Datensatz wäre weder zeitlich noch finanziell sinnvoll.

Kein Data Leakage

Der Verkäufer-Durchschnitt (seller_avg_review_prior) fließt nur aus Bestellungen vor der aktuellen ein — zeitlich sortiert + geshiftet.

pipeline/explain.py # SHAP-Werte + Top-3-Treiber

Limitierungen

  • Kein Anspruch auf produktionsreife Vorhersagegüte (Recall 0,14 — ein relevanter Teil schlechter Reviews wird nicht erkannt).
  • Kein Auth, keine Multi-Tenancy, kein generisches BI-Tool.
  • Kein Live-Postgres, keine Live-Verbindung zu sql-agents Datenbank.
  • Snapshot zeigt eine ~500er-Stichprobe der Bestellungen, nicht alle ~100.000.
  • Backend läuft auf Render Free-Tier — schläft nach Inaktivität ein (Cold-Start ~50s).
